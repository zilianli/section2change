## 高

### 1. 单点立交原路口改造不加臂端坡道，主线悬空

- **位置**：`src/InterchangeMod.Generation/Templates/SinglePointTemplate.cs:143-145`（只调 `AddDualTails`，没调 `AddApproachSlopes`）；对比 `PartialCloverleafTemplate.cs:126-127`、`DiamondTemplate.cs:281`。工具设外部高度：`src/InterchangeMod/Systems/InterchangeToolSystem.cs:1265-1273`；接回的高度容差：`src/InterchangeMod/Placement/RoadRemover.cs:36, 226`。
- **问题**：单点立交的主线固定在上层（≥ 8.5 米）。对准一个地面平交路口改造时，工具把每条臂的 `ExternalElevation` 设成原路口高度（约 0 米），其他模板靠 `AddApproachSlopes` 在臂端加坡道降到这个高度，单点立交没有加。
- **后果 / 复现**：探针用 `DualTailTests` 的单点立交参数（主线 10 米、被交道路 0 米），四条臂 `ExternalElevation = 0`：生成 28 段、坡道 0 段，主线 4 个臂端仍在 Y = 10；同参数的菱形生成 12 段坡道、臂端都在 Y = 0。游戏里 `RoadRemover.Attach` / `FindEnd` 要求臂端与原有道路高差 ≤ 3 米，所以主线两端都接不上：原有道路的切断端再后退 10 米多，主线臂端悬空，路网断开（面板“接回臂端”数会变少）。这正是“平改立”最常见的用法；README 里单点立交的游戏内验证应该是在空地或立体交叉上做的。
- **建议**：在 `SinglePointTemplate.Generate` 的 `AddDualTails` 之后加 `InterchangeLayout.AddApproachSlopes(segments, p);`（与部分苜蓿叶一致），并检查坡道是否压到匝道落地段（单点立交的匝道在主线外侧横移，坡道在 `mainOuter` 之外，应该没有冲突）。同时加一条跨模板测试：设了 `ExternalElevation` 时所有臂端的 Y 都等于它（见“测试缺口 1”）。

### 2. 左侧通行时 `AddDualTails` 把双幅尾段放反

- **位置**：`src/InterchangeMod.Generation/InterchangeLayout.cs:144`（`Vec3 right = Directions.RightOf(dir);`，没有乘左右侧通行的符号，注释 125-127 行也写着“右侧通行”）。调用方：`SinglePointTemplate.cs:144`、`PartialCloverleafTemplate.cs:126`；两者都接受左侧通行（`SinglePointTemplate.cs:186`、`PartialCloverleafTemplate.cs:211/365`）。工具在外部被交道路是双幅时自动换成双向并要求分回双幅：`InterchangeToolSystem.cs:1243-1259`。
- **问题**：驶离立交的那一幅总放在外指方向的右侧，左侧通行时应在左侧。
- **后果 / 复现**：探针按“左侧通行结果 = 右侧通行结果沿主线轴镜像（行驶方向不变）”逐个比较所有接受左侧通行的模板（菱形、单点、苜蓿叶、部分苜蓿叶、快速路十字 / T 型、环岛，含臂端过渡）：全部一致，唯独两者的 4 段 `*-out` / `*-in` 尾段不一致；坐标上左右侧通行生成的尾段完全相同（例如 `Cross-1-out` 都在 z = −6）。游戏里尾段外端正好落在对向那一幅原有道路上（横距 < 6 米），`RoadRemover` 会把它接上：单行道路头对头相接，这一方向的车流走不通。
- **建议**：`right = Directions.RightOf(dir) * (p.RightHandTraffic ? 1f : -1f)`；`DualTailTests` 增加左侧通行用例并断言行驶侧（现在只检查横距绝对值）。

### 3. 弯道上原路口改造的拆除范围圈进大片无关区域

- **位置**：`InterchangeToolSystem.cs:943`（`new Footprint(segments.Select(s => s.Curve), kRemovalMargin)`）；`src/InterchangeMod.Generation/Geometry/Footprint.cs:16-28`（凸包）；`RoadRemover.cs:56-86`（范围内、离任一层 4.5 米内的普通道路都拆）。
- **问题**：拆除范围是所有新路段的凸包外扩 2 米。直线立交的凸包基本贴着道路；弯道上整座立交被弯成弧形，凸包会把弧内侧的弓形区域整片包进去。`FindEdges` 不区分是不是被改造的那两条路，范围内高度接近的道路一律拆掉，范围外的部分在边界处切断、不接回。
- **后果 / 复现**：探针用菱形（主线高架 10 米、地面被交道路、原路口改造时主线两端下坡接回）按主线半径弯曲后统计范围面积：

  | 主线 | 范围面积 | 其中离任何新路 > 50 m | > 100 m | 最远点 |
  |---|---|---|---|---|
  | 直线 | 15.4 ha | 1.2 ha | 0 | 68 m |
  | R 1000 | 17.6 ha | 4.9 ha | 1.0 ha | 127 m |
  | R 600 | 22.0 ha | 10.0 ha | 5.3 ha | 206 m |
  | R 300 | 23.9 ha | 12.4 ha | 7.8 ha | 271 m |

  弯道内侧如果有街区、停车场出入口、辅路，在地面层（或上层 ±4.5 米）的部分都会被拆，并在范围边界留下断头路。预览里能看到，也能撤销，但面板只显示“拆除 N 条”，玩家很难注意到几百米外的支路被切断。苜蓿叶、定向式这类大立交的象限区域同理（直线时也会包进象限里的道路，只是那里本来多半要让出来）。
- **建议**：范围改成非凸的“走廊并集”：每段新路按半宽 + 余量做缓冲（采样成胶囊或折线外扩），`Contains` 判断点到最近新路段的距离；或者只拆与匹配到的那两条路相连（`m_MatchEdges` 沿路追下去的路段、立体交叉的 `m_CrossingEdges`）以及真正与新路走廊重叠的路段。`kConnectInside = 300` 那一套“臂端外仍在范围里的路段整段保留”的补丁也可以随之简化。

### 4. 路口两侧道路形式 / 预制体不同时只取一侧

- **位置**：`src/InterchangeMod.Generation/Junctions/JunctionMatcher.cs:176-186`（十字：`result.Main = mainLeg.Road`，另一臂的 `Road` 丢掉）、`:291-295`（T 型同样）；主线 / 被交道路的排序也只看 `p.a`（`:171-175`）。工具只按 `m_Match.Main/Cross` 给两端设同一种形式：`InterchangeToolSystem.cs:1144-1158, 1166-1167`，从不按臂设 `ExternalForm`。接回横距：`RoadRemover.cs:38`（6 米）。
- **问题**：`DescribeLeg` 对每条臂分别识别了双向 / 双幅、分隔带、预制体，但匹配结果每条路只留一条臂的信息。道路在路口处换形式（双幅在路口变成双向、车道数变化）很常见。
- **后果 / 复现**：探针造一个十字路口：北臂双幅公路（两条 3 车道单行），南臂双向 `Large Road`，东西双向。当前朝向 0° 时匹配出 `main = Hwy OW, Dual`；朝向 180° 时变成 `main = Large Road, TwoWay`——取决于朝向，另一侧总是丢失。立交两端都按同一形式建：若按双幅建，南端两个臂端离原有双向道路中心线各 (分隔带 + 宽) / 2（例中约 8 米 > 6 米），接不上，原有道路切断端后退，留下缺口；分隔带窄时（< 6 米）会把双向道路只接到其中一幅上，另一方向的车流断开。若按双向建，北端同理。
- **建议**：`JunctionMatch` 增加每条臂的 `MatchedRoad`（形式、预制体、宽度、分隔带），工具按臂设置 `ExternalForm / ExternalPrefab / ExternalWidth / ExternalMedian`，模板已有的过渡段（双幅 → 双向的 `AddTransition`、双向 → 双幅的 `AddDualTails`）就能接上；暂时不支持的组合至少给出“路口两侧道路形式不同”的明确报错，而不是静默建一个接不回的立交。

### 高严重性的修复（第 1–4 条）

1. 单点立交生成末尾加 `AddApproachSlopes`；新增跨模板测试 `ApproachSlopeTests`：13 种类型在原路口改造（外部高度 0 米）时所有臂端都落到 0 米、坡度不超限（只有单点立交原来不满足）。
2. `AddDualTails` 的驶离一侧乘左右侧通行的符号；`DualTailTests` 加左侧通行用例并断言哪一幅在哪一侧（不改时 4 个左侧通行用例失败）。
3. 拆除分两种范围：被改造的道路（匹配到的路口 / 立体交叉的路段，沿路经过普通路中节点往外、仍和凸包相交的各段）照旧按凸包拆；其他道路只拆被新路压到的部分（`Footprint.Corridor` + `Collides`：平面上离新路中心线不到“新路半宽 + 2 米 + 自己的半宽”，并且按实际离地高度没有净空——高差不到 7.5 米，新路在那里是路堤 / 路堑时按实心 / 开口算；或落在新路高架节点的立柱上。高架匝道下面净空够的地面道路保留，2026-10-27 游戏内反馈后定）。`JunctionReader.Read` 输出路口的全部路段。测试：网格查找与暴力计算一致、垂直穿过的街道在新路边外切开、弯道菱形的走廊不离开新路、各种高差 / 路堤 / 路堑 / 立柱的判断。
4. 不修（2026-10-27 决定）：一条路在路口两侧形式不同的情况不专门支持，立交按其中一侧建，另一侧由玩家放置后自行连接；只需支持两条路（两层）是不同类型的道路（已支持，如高架双幅公路跨地面双向道路）。曾做过按臂过渡的实现（主线一端变双向时单点立交、喇叭形以外都能过渡），已撤回。

### 5. 固定预览或鼠标在面板上时改“上层道路 / T 型主线”不重新定向

- **位置**：`InterchangeToolSystem.cs:445-451`（固定或鼠标在 UI 上时不调 `UpdateJunctionMatch`）、`:563-575`、`:582-624`（`OrientCrossing` 只在 `UpdateJunctionMatch` 里调用）；误报的错误：`:1274-1275`。
- **问题**：立体交叉时哪条已有道路当主线由 `OrientCrossing` 按“上层道路”（`MainOnTop` / `CloverleafCrossOnTop`）和 `TeeMainRoad` 对调；同层十字当 T 型时“主线：换另一条”也靠它。但在面板上改这些设置时鼠标必然在 UI 上，固定后更是一直不调用。
- **后果 / 复现**（推断）：对准“高架公路跨地面道路”的立体交叉，选菱形，左键固定，然后把“上层道路”改成主线：`MainOnTop` 变了，但匹配结果没对调（主线仍是下面那条），面板报“这处立体交叉里被交道路在上层：该立交类型的主线必须在上层，请换成菱形立交”——当前就是菱形；确认按钮被禁用，直到取消固定。苜蓿叶 / 部分苜蓿叶 / 环岛改 `CloverleafCrossOnTop` 一样。同层十字当 T 型时选“换另一条”，固定期间预览完全不变。没固定时则是鼠标回到地图上才纠正，期间面板显示错误。
- **建议**：`NotifySettingsChanged` 后（或 `UpdatePreview` 开头）调用一次 `OrientCrossing()`；固定在匹配上（`m_PinnedOnMatch`）时朝向要跟着新的 `m_Match.MainAngle` 更新（现在固定时用 `m_LastYaw`）。

### 6. Y 型分向按相对高度缓存布置，基层平移后复用旧分段

- **位置**：`src/InterchangeMod.Generation/Templates/WyeTemplate.cs:147-158`（布置缓存键：高度减去基层，只附加基层和第二层的高度段）、`:923`（分段时按**绝对**高度判断是否高架、高架段 ≤ 70 米）。定向 T 型是同样的写法：`DirectionalTTemplate.cs:153-165, 806-818`。
- **问题**：缓存键只区分 `h0`、`h0 + g`（定向 T 型还有 `h0 + 2g`）所在的高度段，但匝道中间各点是否 ≥ 8.5 米随 `h0` 连续变化；复用的布置是按第一次求解时的绝对高度分段的。
- **后果 / 复现**：探针：同一个 `WyeTemplate` 实例先在基层 0 米生成，再在基层 3.5 米生成（两者都是“地面”段，第二层都是高架），结果与新实例在 3.5 米直接求解不同：48 段 vs 51 段，复用结果里有 3 段高于 8.5 米、长度超过 80 米的路段（重新求解时这些都切成 ≤ 70 米）。游戏会自己把它们等分，切点的立柱不受控制，可能落在下面的道路上（报“与现有物体重叠”）。面板里按 0.5 米一档调基层、或对准路堤上的路口时都会走到。定向 / 半定向 T 型在 0→3.5、0→−3.5、4.2→8.2 三组下没有复现，但写法相同，有同类风险。
- **建议**：分段（cut）不进缓存，每次按实际高度重算（它比转弯半径搜索便宜得多）；或者把“每条匝道跨过 8.5 米的位置”量化后放进缓存键。加一条测试：先 `Generate(base 0)` 再 `Generate(base 3.5)` 必须等于新实例 `Generate(base 3.5)`。

### 7. 两条单行道路都驶入同一节点时匹配器抛异常

- **位置**：`JunctionMatcher.cs:219`（`.First(e => e.TravelOutward)`）。
- **问题**：指着一条普通道路（两个方向）且两侧都是单行道路时，默认至少有一条是驶离节点的。两条单行道路在一个节点相向汇入（玩家画反了方向、或一条单行路的尽头接另一条单行路的尽头）时没有。
- **后果 / 复现**：探针：两条 `OneWay = true, TravelOutward = false`、方向相反的路段 → `InvalidOperationException: Sequence contains no matching element`。在游戏里异常从 `OnUpdate` 抛出，鼠标停在那里时每帧都抛，工具不再更新预览。
- **建议**：`FirstOrDefault`，取不到时 `Fail(result, "这条路两侧的单行道路方向相对，无法判断双幅方向")`。`DescribeLeg` 已有类似的防护（`:378-381`）。

### 8. 只对齐一条弯道时每帧重新求解，弯道收紧坡度让缓存失效

- **位置**：`InterchangeToolSystem.cs:676-678`（只对齐一条路时每帧按鼠标重新匹配，中心和中心线都变）、`:907-918`（每次重建都 `Bend`）；`src/InterchangeMod.Generation/InterchangeLayout.cs:51`（`tighter.MaxGrade = used.MaxGrade * p.MaxGrade / worst * 0.97f`）；定向式 / 涡轮 / Y 型 / 定向 T 型的布置缓存键包含 `MaxGrade`（如 `StackTemplate.cs:148-153`）。
- **问题**：沿弯道移动鼠标时每帧都要弯曲；内侧坡度超限时 `Bend` 按超出比例收紧坡度重解，收紧值随 `worst` 连续变化，几乎每帧都不同，带缓存的模板每次都完整求解（最多 3 次）。
- **后果 / 复现**：探针（.NET 8 Release，游戏的 Mono 会更慢）：定向式首次求解 173 ms、同参数再解 1.2 ms；两条路都是 R 600 时 `Bend` 定向式 145 ms、涡轮 333 ms（坡度从 8% 收紧到 4%）。也就是沿弯道每移动一帧都可能卡 0.1–0.5 秒以上。README 的“生成 < 100 ms”在这种情况下达不到。
- **建议**：收紧后的坡度向下取整到固定档位（例如 0.25%），相邻帧能命中缓存；或者鼠标移动时只用上次的 `used` 参数做弯曲预览、停下或固定时才完整重解；`Bend` 的结果也可以按（模板键、中心线形状量化）缓存。

### 9. 鼠标停在道路上时每帧完整重读立体交叉

- **位置**：`InterchangeToolSystem.cs:644, 708-719`（先 `ReadCrossing` 读完，再比较 `key`）；`src/InterchangeMod/Placement/JunctionReader.cs:158-182, 217-276`（`CollectAt` 对每条收集到的路段两半各追踪 2000 米，4 米一个点）、`:194-207, 298-336`（找不到交叉时 `ReadTee` 再做两层嵌套的空间查询）。每帧还有 `GetNetSearchTree(...).Complete()`。
- **问题**：只要鼠标在道路上、没固定、不在面板上，每帧都执行全部读取和追踪，然后发现键和上次一样就丢掉。普通路口也先走一遍 `FindCrossings + ReadTee`。
- **后果**（推断）：每帧几千个点的分配和 `ConnectedEdge` 遍历，加上空间树的同步点；在密集城区悬停时是持续的主线程开销。指着同一处双幅交叉的另一幅时键也会变，触发整座立交重建。
- **建议**：先只做 `FindCrossings` + 取最近交叉得到键（或 `ReadTee` 的 `(Main, Branch)`），键没变就返回；只在键变化时 `CollectAt`（追踪）。键可以改成无序的道路对（同一处交叉的两幅算同一个）。

### 10. `FitRampLength` 对不用匝道长度的模板失败时试 31 次；喇叭形没有缓存

- **位置**：`InterchangeLayout.cs:21-31`；`InterchangeToolSystem.cs:885`（每次重建都调）；缓存键含 `RampLength`：`CloverleafTemplate.cs:111, 131, 145`、`PartialCloverleafTemplate.cs:107, 139, 169`、`RoundaboutTemplate.cs:107, 124, 154`；`TrumpetTemplate.cs:128-163`（每次 `ValidateParams` / `Generate` / `ResolveLoopRadius` 都重新搜索半径）。
- **后果 / 复现**：喇叭形、苜蓿叶、部分苜蓿叶、环岛不用 `RampLength`，参数检查失败时（如手动环道半径太小）`FitRampLength` 每档加 10 米试满 31 次，每次键都不同、缓存全部失效。探针：苜蓿叶成功 0.6 ms / 次，手动半径 30 米时 12 ms / 次；喇叭形成功 2.2 ms、失败 6.4 ms。每次移动鼠标都付这笔开销。

### 11. 静态缓存不是线程安全的，测试并行时会串结果

- **位置**：`CloverleafTemplate.cs:124-127`、`PartialCloverleafTemplate.cs:162-165`、`RoundaboutTemplate.cs:147-150`（`s_plan`、`s_planKey` 等分开赋值的静态字段）。测试项目没有关闭并行（无 `CollectionBehavior` / `xunit.runner.json`），xunit 默认按测试类并行；苜蓿叶同时被 `CloverleafTemplateTests`、`CurvedRoadTests` 使用，部分苜蓿叶被 `DualTailTests`、`PartialCloverleafTemplateTests` 使用。
- **后果 / 复现**：探针 4 个线程各 300 次 `new CloverleafTemplate().Generate(...)`（5 种交角随机）：1200 次中有 1 次拿到了别的参数的结果。游戏里只有主线程，不受影响；测试会偶发失败、难以重现。
- **建议**：改成实例字段（定向式、定向 T 型、Y 型已经是实例字段），或把（键, 值）存成一个不可变元组一次赋值；必要时给这几个测试类放进同一个 `[Collection]`。

### 12. 面板与 C# 取值范围不一致

- **位置**：`src/InterchangeMod.UI/src/mods/InterchangePanel.tsx:150`（苜蓿叶交角 35–145°）对 `src/InterchangeMod/Setting.cs:242`（一律限制在 45–135°）；`InterchangePanel.tsx:320-324`（环岛半径最大 300，`RoundaboutTemplate.cs:40` 也是 300）对 `Setting.cs:262`（限制 30–250）；`InterchangePanel.tsx:355-357` 与 `InterchangeToolSystem.cs:605-611`（`TeeMainRoad`）。
- **后果**：苜蓿叶在 45° 时按“−”发出 40，C# 限制回 45，按钮不禁用但没反应；喇叭形模板允许 35–145°（`TrumpetTemplate.cs:30`），面板和设置都到不了。环岛自动半径大于 250 米时切到“手动”，面板发出的取整半径被限制成 250，马上报“环岛半径至少 N 米”。同层十字选过“换另一条”（`swap`）后再对准立体交叉，面板显示“自动”，C# 却按“上层”处理（跳过了“公路优先”）。
- **建议**：范围常量集中一处（例如 C# 把各模板范围放进状态 JSON，面板按它显示）；`TeeMainRoad` 在立体交叉下把 `swap` 当 `auto`。

### 13. 确认放置后立即按旧匹配在原处重建预览

- **位置**：`InterchangeToolSystem.cs:430-438, 445-451, 478-492`。
- **问题**：确认后 `m_HasPreview = false`、`m_Pinned = false`；下一帧鼠标还在“确认放置”按钮上，走“鼠标在 UI 上”分支，用 `m_LastOrigin / m_LastYaw` 和旧的 `m_Match` 重建预览。
- **后果**（推断）：刚建好的立交上马上又叠一座预览，原路口改造逻辑会把刚建好的路段标成拆除并重建；面板显示新的拆除数和游戏报错，直到鼠标回到地图。不会误放（确认需要再次固定），但容易让人以为没放成功。
- **建议**：确认成功后清掉 `m_Match / m_MatchEdges / m_CrossingKey / m_HasOrigin`，或在下一次鼠标进入地图前不重建预览。

### 14. 重新打开工具时沿用上次会话的原点和匹配

- **位置**：`InterchangeToolSystem.cs:345-362`（`OnStartRunning` 只重置固定状态）、`:445-451`。
- **后果**（推断）：用左上角按钮打开工具（鼠标在 UI 上），在首页点一种立交后，预览出现在上一次关闭工具时的位置，用的是那时读出的路口；如果那里已经建了立交，预览会把它标成拆除。鼠标移到地图上后恢复正常。

### 15. 状态 JSON 遇到 NaN / Infinity 会让整个面板消失

- **位置**：`src/InterchangeMod.Generation/Text/JsonText.cs:33, 66`；`src/InterchangeMod.UI/src/mods/bindings.ts:232-238`；`InterchangePanel.tsx:52, 59`。
- **问题**：`float.NaN.ToString("0.###")` 输出 `NaN`、无穷输出 `Infinity`，都不是合法 JSON；面板 `parseJson` 失败时退回 `{active:false}`，面板直接不显示，没有任何提示。现在的字段大多已处理（半径把无穷换成 0），但例如路段切线退化时 `JunctionMatcher.MeanDirection` 的 `Normalize(0)` 会把 NaN 带进 `MatchAngle`。

### 16. `Fingerprint` 漏掉 `HeightRange`

1. **跨模板不变量**（最值得补，能直接抓到第 1、2 条）：
